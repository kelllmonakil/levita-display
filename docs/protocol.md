# Протокол экрана Thermalright (87AD:70DB, bulk)

Метки достоверности:
**«подтверждено захватом»** — видно в нашем pcapng/USB-логе;
**«взято из trcc-linux»** — документация/код проекта Lexonight1/thermalright-trcc-linux
(декомпиляция `USBLCDNEW.exe` 2.3.0 и C# TRCC 2.1.x);
**«гипотеза»** — вывод по аналогии, не проверен;
**«неизвестно»** — данных нет.

Дополнительная метка **«подтверждено ответом устройства»** — байты пришли от панели в
ответ на хендшейк (не pcap, но и не догадка). Захвата USB-трафика у нас пока нет.

Ни одна строка не помечена «подтверждено захватом»: на устройство мы ничего не писали и
трафик не снимали.

## 0. Факт для нашей панели (2026-10-31)

Ответ на хендшейк, `docs/report-stage0.txt`:

```
PM = 64, SUB = 3, FBL = 114
resolution = 1600x720 (JPEG)
raw[0:64] = 12345678 53534352 4d2d5633 00000000 00000000 772f0b9b
            40000000 20000000 0f000000 03000000 03000000 01000000
            282703fe 00000000 81000000 00000000
```

- `12 34 56 78` — magic совпал. — *подтверждено ответом устройства*
- `SSCRM-V3` в байтах 4..11 (ASCII) — строка платформы/прошивки. — *подтверждено ответом
  устройства*; её смысл — *неизвестно*
- `PM = 0x40 = 64`, `SUB = 0x03 = 3`. — *подтверждено ответом устройства*
- `resp[56] = 0x81` → ветка A, имя = hex из `resp[48:52] = 282703fe`.
  — *подтверждено ответом устройства*
- Разрешение 1600×720 и JPEG — *взято из trcc-linux*, применено к нашим байтам.
- Пара (64,3) в `variants.py` подписана как Levita. — *взято из trcc-linux*
- 2400×1080 из спецификации Thermalright с этим ответом не согласуется. — расхождение,
  *неизвестно*, что видит пользователь; проверяется сеткой.
- Байты 20..23 (`77 2f 0b 9b`), 32 (`0x0f`), 40 (`03`), 44 (`01`) — *неизвестно*.

## 1. Транспорт

- USB Bulk, vendor-specific (bInterfaceClass = 255).
  — *взято из trcc-linux* (`doc/PROTOCOL_USBLCDNEW.md`, `adapters/device/bulk_lcd.py`)
- EP write = `0x01` (OUT), EP read = `0x01` (IN).
  — *взято из trcc-linux*
- На Windows нужен WinUSB-совместимый драйвер (libusb/WinUSB).
  У нас уже стоит `winusb.inf` от Microsoft — **факт** (проверено `Get-PnpDeviceProperty`),
  поэтому Zadig не требуется.
- Устройство наше: `USB\VID_87AD&PID_70DB\29090E191AB41704`, REV_0407, дескриптор
  `USBDISPLAY`, статус OK — **факт**.

## 2. Хендшейк (запрос информации об устройстве)

Отправка 64 байта:

```
offset 0..3   : 12 34 56 78          (magic)
offset 4..55  : 00 …
offset 56     : 01                   (команда «device info»)
offset 57..63 : 00 …
```

Чтение: 1024 байта, таймаут 1000 мс.

Разбор ответа:

| Поле | Источник | Смысл |
|---|---|---|
| валидность | `resp[24] != 0` | PM (product mode), ненулевой = устройство ответило |
| PM | `resp[24]` | модель/семейство |
| SUB | `resp[36]` | под-модель, также задаёт монтаж/поворот |
| имя | `resp[32..51]` | при `resp[56] == 0x81` — 4-байтовый hex-ID |

— *взято из trcc-linux* (`bulk_lcd.py::_do_handshake`, `PROTOCOL_USBLCDNEW.md`)

Это **чтение**, не запись изображения. Именно его выполняют `trcc detect/report/device state`.
Для нашей панели корректность ответа — *гипотеза*, пока не увидим вывод пользователя.

## 3. Определение модели и разрешения

- База для bulk-семейства: FBL 72 → 480×480.
- Если PM/SUB есть в «pm ladder» C#, FBL переопределяется:
  `63 → 114`, `64 → 114` (оба 1600×720).
  — *взято из trcc-linux* (`core/protocol.py::_PM_TO_FBL_OVERRIDES`)
- `variants.py`: комментарий «PM=64 SUB=3: Levita (new product) handshakes identically to
  LM30»; PM 63 SUB 3 — вариант `A1LM30`.
  — *взято из trcc-linux* (комментарий автора, не наш замер)
- Подтверждённый тестером `@oranura` экземпляр «Levita Vision» — 1600×720.
  — *взято из trcc-linux* (`doc/REFERENCE_DEVICES.md`)
- В библиотеке **нет** разрешения 2400×1080.
  — *факт* (grep по установленному пакету)
- Заявленные производителем 2400×1080 против 1600×720 в библиотеке — *неизвестно*, что верно
  для USB-холста. Оба варианта 20:9. Проверяется одним статичным кадром-сеткой (Этап 3/4).
- Наша панель ответила PM=64/SUB=3 → библиотека выдала **1600×720**.
  — *подтверждено ответом устройства* (сама трактовка PM→FBL — *взято из trcc-linux*)

## 4. Кадр

64-байтный заголовок + payload, little-endian:

| Offset | Размер | Значение |
|---|---|---|
| 0..3 | 4 | `12 34 56 78` (тот же magic) |
| 4..7 | 4 | команда: `2` = JPEG, `3` = RGB565 |
| 8..11 | 4 | ширина холста |
| 12..15 | 4 | высота холста |
| 16..55 | 40 | нули |
| 56..59 | 4 | `2` (константа в библиотеке) |
| 60..63 | 4 | длина payload в байтах |

Передача: кусками по 16 КиБ в EP01 OUT, таймаут 5000 мс; если `(64 + len) % 512 == 0`,
после последнего куска отправляется zero-length packet.

— *взято из trcc-linux* (`bulk_lcd.py::_prepare_frame`, `_write_frame`)

Замечание: в документации `PROTOCOL_USBLCDNEW.md` сказано, что длина в shared memory
лежит в `bytes[60:63]`, и общая передача = `len + 64`. Это совпадает с кодом библиотеки.
Формулировка «`bytes[60:63]`» там неточная (4 байта — `60:64`), используем код.

## 5. Кодирование пикселей

- PM 63/64 → **JPEG** (`cmd=2`). RGB565 только для PM 32 и 50.
  — *взято из trcc-linux*; для Levita 360 — *гипотеза* (зависит от фактического PM).
- Размер JPEG-кадра не фиксирован (зависит от качества/содержимого), поэтому пропускная
  способность USB — главный кандидат в узкое место.
- Для справки, если бы это был RGB565: 1600×720×2 = 2 304 000 Б; 2400×1080×2 = 5 184 000 Б
  на кадр — при 60 Гц это 138 и 311 МБ/с, что для USB 2.0 (реально ~35–40 МБ/с) невозможно.
  Поэтому JPEG — не случайность, а необходимость.
- Поворот кодируется **до** отправки (библиотека крутит изображение и/или меняет базу
  поворота в зависимости от SUB). Панель получает уже «правильно ориентированный» кадр.
  — *взято из trcc-linux* (`core/protocol.py::resolve_encode_rotation`)

## 6. Поворот и монтаж

- `ENCODE_ROTATIONS` для 1600×720: база 180°, но при `SUB == 3` → **0°**.
  — *взято из trcc-linux*
- Портретный монтаж вычисляется из SUB (`is_portrait_mounted`) в адаптере Bulk.
  — *взято из trcc-linux*
- Для нашей панели фактические значения неизвестны до хендшейка.
  Признак поворота: если картинка-сетка выходит боком/вверх ногами — это правило
  `SUB`-поворота, а не дефект кодирования.

## 7. Keepalive

- Bulk-семейство возвращается к логотипу через ~2–3 с после последнего кадра
  (`FAST_REVERT_KEEPALIVE_S`). Значит поток кадров должен быть непрерывным, либо нужно
  периодически повторять последний кадр.
  — *взято из trcc-linux*

## 8. Чего мы НЕ будем делать

- `SSCRM_CMD_TYPE_OTA = 4`, `LOGO = 3`, `UPG_STATE = 5`, `LOGO_STATE = 9` — не отправляем
  вообще. Это обновление прошивки / заставка / состояние апгрейда.
- `BKL_SET = 8` (яркость), `ROTATE = 6`, `SCR_SET = 7` — только после отдельного
  согласования с пользователем и только если понадобятся.
  — *взято из trcc-linux* (константы C#)

## 9. План проверки (Этап 3, Вариант A)

1. Хендшейк → PM/SUB/разрешение. Никаких кадров. Сверить с ожиданием (63/64, SUB 3, 1600×720).
2. Один статичный кадр 1600×720: заливка известным цветом (или сетка с метками).
   Показать пользователю точный список вызовов **до** отправки.
3. Если картинка растянута/обрезана/занимает часть экрана — проверить гипотезу 2400×1080,
   отправив кадр этого размера (заголовок с другими width/height).
4. Затем поток кадров и замер FPS/загрузки CPU.

## 10. Открытые вопросы

- Реальный PM/SUB нашей панели — *неизвестно*.
- Реальный холст: 1600×720 или 2400×1080 — *неизвестно*.
- Видимая область (изогнутый AMOLED, «5.5:4.5») — *неизвестно*, Этап 4.
- Принимает ли прошивка JPEG с другим качеством/подвыборкой — *неизвестно*.
